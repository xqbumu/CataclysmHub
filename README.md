# Cataclysm Hub

本地优先的 Cataclysm 游戏与多版本游玩实例、模组、声音包、存档和独立备份管理器。当前为 Tauri 2 + React + Rust 桌面开发预览。

## 当前能力与验证范围

- 游戏库：导入可信程序或 macOS `.app`，管理多个安装版本，创建各自独立的游玩实例；已保存普通方案可一次点击启动。
- 游戏获取：DDA、BN、TLG、EOD、TISH 官方发布目录，首次自动同步尝试，之后手动更新，下载有进度、取消和摘要检查。
- 资源：本地模组、声音包登记与受控安装，按关联安装及实例检查和配置；配置发布前保护原文件，可检查历史并回滚。
- 存档保护：只读扫描、工作区或实例完整备份、回读验证、恢复到新目录、独立恢复结果检查、名称/备注/保留锁和只读保留规则预览。
- 任务与记录：直接进程监测、资源冲突检查、持久任务状态与审计，重启后中断任务不自动重放。

本机 macOS Apple Silicon 的 H/I QA 样本分别完成 Hub 启动、建档、保存和再次加载。样本是经过记录调整的 QA 应用包，不代表原始发行包、任意变体或其他系统已认证。普通启动方案保持全局互斥；同时游玩仅有显式实验候选，正式多版本并发尚未验收。Git 历史、覆盖原目录恢复和跨版本存档迁移尚未交付。

## 快速开始

1. 首页“游玩环境”提供“获取游戏”和“导入已有游戏”两个入口；已有安装可在引导中直接选择。
2. 首次使用先确认数据位置：可沿用系统推荐值，点击“保存位置并继续”；自定义子目录默认收起。此步骤复用原目录检查，不迁移旧文件。
3. 导入可信程序或 macOS `.app` 并确认名称；下载路径则先下载/解压，再选择实际程序导入。应用包必须有唯一受支持的真实入口，不执行包内启动脚本。
4. 为游玩环境命名，确认创建当前数据根目录下的独立目录。登记后不会自动启动，也不会自动复制旧存档。切换导航可返回继续引导；退出应用后仍可使用已登记的安装或环境。
5. 点击“前往启动”返回首页，新建环境优先显示。已支持安装首次启动进入方案确认，之后保存的普通方案可一次点击启动；未知安装仍需人工核对，高级设置用于排障或实验。
6. 游戏创建世界并保存退出后，在“存档与备份”选择对应实例建立保护副本。进程退出不自动证明存档稳定，也不会自动生成检查点。

实例有活动会话时，启动按钮显示“启动中”或“运行中”，退出后恢复。“待确认关闭”表示上次会话状态未知，请先检查游戏是否仍在运行，再通过“任务与记录”确认关闭。

macOS 若启动后立即结束：先查看首页异常提示和“任务与记录”，再核对系统安全提示及实例 `config/debug.log`。被信号终止不等于已证实被 Gatekeeper 拦截；需系统日志确认。先关闭系统拦截弹窗（不要移到废纸篓），再查看“隐私与安全性”的对应“仍要打开”。完成 Touch ID 或管理员验证后，返回 Hub 启动；若系统自动打开游戏，先退出并核对目录。若仍没有对应入口，不要反复启动或直接双击原 `.app`：部分官方脚本会丢弃独立目录参数，可能采用游戏默认目录。Hub 不会自动移除隔离、更改签名或关闭系统保护；单独授权前先确认来源与具体副本。详情见 [macOS 启动排障与授权边界](docs/quality/macos-authorization-2026-10-30.md)。

对于已识别的 macOS 样本，异常结束提示的“高级排障”中提供“检查此安装的隔离属性”（优先系统正常授权）：先只读核对完整范围，再由用户单独确认是否仅移除此安装的隔离属性，执行前保留属性记录。该动作会绕过首次隔离检查，不是正常 Gatekeeper 授权；不自动启动，也不代表兼容认证。未明确拦截时应先排查其他原因，详见 [处理边界](docs/design/macos-installation-trust.md)。

macOS 若在复制游戏包后出现 `Stale game data detected`，不要连续忽略错误。退出测试副本，优先使用干净发行包复验；制作带缓存的 QA 副本时需保留文件时间戳。本机实验中普通复制改变时间戳后报错，保留时间戳的新副本正常进入主菜单；这不是所有此类错误的通用修复。不要为此删除玩家存档或修改原包，详见 [原生启动实验](docs/quality/nsworkspace-launch-probe-2026-10-29.md)。

## 游戏与资源的下载缓存

在“游戏库 → 获取游戏”或“模组与声音 → 下载资源”选择上游附件。相同附件先核对缓存大小与 SHA-256，可用时离线复用，缺失或损坏才重新下载；页面显示本机系统与架构的文件名匹配提示。目录首次同步后仅手动更新。

下载后可确认解压 ZIP、普通 TAR、TAR.GZ 到独立新目录并复制路径；DMG、7z、含链接或扩展记录的包使用系统工具处理。解压不执行软件、不覆盖安装或实例。删除下载包保留已解压目录和记录。游戏解包后通过本地导入登记，资源合集解包后逐个登记需要的包。

配置资源时选择关联安装和实例，读取后在“修改配置”按名称添加/排序新世界默认模组、选择声音包和开关，再走差异预览、保护副本、确认应用与回滚流程。已有世界组合单独只读；声音切换需重启。资源来源库可通过“部署到游玩实例”将单包复制到明确实例的 mods/sound 新目录（当前 macOS/Linux 实现，Linux 运行待验）；重复 ID 拒绝，不覆盖已有资源。部署后重新读取实例配置，不会修改世界组合。详见 [下载与实例配置边界](docs/design/download-cache-and-instance-content.md)。

下载过程中切换主页面后，重新进入下载页会恢复当前传输的进度与取消入口。新世界默认模组不会允许添加标记为过时的模组；旧世界对这些模组的引用保留。新实例尚未生成配置文件时，对应编辑会禁用并提示先在游戏中保存设置，再重新读取；不会自动猜测或覆盖游戏配置。

设置页的“集中游戏配置”可按安装和实例读取游戏语言、自动保存开关及回合/分钟间隔，再进行保护备份、确认应用与回滚。它修改游戏配置，Hub 界面语言不在本次范围。缺失字段不会自动补写，语言可用性取决于发行包。游戏获取页可按完整 tag 查询历史发布（例如 `0.H-RELEASE`）；已解压记录支持打开目录及从该目录开始选择程序或单包登记。详见 [集中游戏配置](docs/design/common-game-configuration.md)。

## 目录配置和存档管理规则

### 一个数据根目录，可按需覆盖

默认布局如下，目录在保存设置或创建实例时准备：

```text
所选根目录/
├── saves/       工作区存档扫描与整根备份的来源
├── backups/     独立归档、收据及配置保护副本
├── content/     本地模组和声音资源管理目录
└── instances/
    └── 唯一实例ID/
        ├── save/        该实例的世界与角色
        ├── config/      该实例的游戏配置
        └── .hub-runtime/ 适配方案使用的 HOME、临时和 XDG 目录
```

初始只需选根目录。展开“自定义子目录与路径操作”可分别指定存档、备份、资源目录；例如将 backups 指向外置磁盘，“跟随根目录”可恢复该项默认值。根目录独立持久化，覆盖 saves 不会改变新实例的根目录。旧工作区不会自动迁移，旧实例继续使用登记时的绝对路径。

首次选择根目录会生成三个默认子目录；已有工作区切换根目录时，存档和资源使用新根目录，备份默认保留原位置，避免历史记录失联。确需改备份目录时，可在该项点击“跟随根目录”，后端仍会检查历史引用。设置保存后仍可修改。更改配置**不移动、不复制、不删除原文件**；先核对目标目录，再勾选确认保存。修改影响工作区扫描和后续操作，新托管实例使用当前根目录；已登记实例、资源及安装不会自动重新绑定。活动或未知游戏会话、文件任务占用期间不能改目录，过期草稿不能覆盖更新后的目录。

已有备份、备份/恢复任务或配置保护记录时，备份目录变更会被拒绝，以保留历史记录的可访问性。调整其他目录时保留原备份路径；当前没有自动迁移备份库功能。不要仅在文件浏览器搬走归档后修改路径。设置页提供目录复制和打开按钮；实例数据路径可点击复制，旁边按钮打开文件浏览器。

同一个根下的 backups 与 saves 是不同目录，但仍可能位于同一磁盘，不能抵御整盘损坏；需要设备故障保护时覆盖备份目录到独立介质。元数据 SQLite、元数据升级副本和 Hub 配置重置备份位于系统应用数据目录，不属于游戏存档。下载原始包及可重建缓存仍使用应用管理位置；content 保存已登记/安装的资源，下载并不自动启用资源。

### 世界、实例和版本的关系

一个游戏安装可关联多个实例；每个实例有自己的 save/config，世界与角色由游戏创建和维护。工作区 saves 与实例 save 是不同来源：工作区扫描不会自动汇总所有实例；在备份页选择相应实例建立该实例保护副本。不要把实例目录与安装、工作区子目录或其他实例相互嵌套。

游戏版本识别依据登记程序摘要，启动时重新检查程序；目录名和版本标签不能证明存档兼容。H 样本使用 `.sav`，I 样本使用 `.sav.zzip`；Hub 以文件集合保护数据，不改写角色格式。升级游戏时应保留原安装和原实例、先备份，再在独立实例验证。不要让不同版本共用同一个世界，不能根据“归档校验通过”推断跨版本可加载。

实例备份恢复到新目录后，可在“游戏库 → 游玩实例 → 登记新实例”选择原游戏安装，再选择恢复容器内的 `data/` 作为新实例目录。登记时重新回读核对归档和恢复文件；只有 Hub 记录为成功恢复、来源实例及安装摘要可核对、文件完整且无未完成标记的数据才允许使用。普通非空目录仍拒绝。这不会覆盖或切换原实例，也不证明跨版本兼容。备份预览若提示 `save` 没有普通文件，仍可保护配置，但不等于已经保存了游戏进度。

游戏除实例目录外还可能更新安装内 JSON/gfx 缓存，因此冲突检查需要覆盖完整安装和实例目录。自定义方案、系统 API 或外部进程可能写到其他位置；传递目录参数不是系统沙箱。退出游戏并确认相关子进程已关闭，再开始备份、配置发布或恢复。

### 配置重置

设置页“备份并重置 Hub 配置”先保存旧配置 JSON，成功后重置每实例启动偏好及本次界面筛选。备份失败不重置；保留工作区目录、安装、实例、资源、存档和恢复保护记录，不重置游戏内配置。目录迁移不属于重置。

## Taskfile 开发入口

安装 Task 3 后，在仓库执行 `task --list` 查看任务。原 npm / Cargo 命令仍可直接使用。

| 命令 | 用途 |
|---|---|
| `task deps` | `npm ci` 并获取锁定的 Rust 依赖 |
| `task dev` / `task dev:web` | 桌面开发 / 浏览器预览 |
| `task check` | 顺序执行前端、全特性 Rust 和 Python 检查 |
| `task check:frontend` / `task check:rust` / `task check:python` | 单独检查 |
| `task bindings` | 更新前端 DTO |
| `task build:frontend` | 前端生产构建 |
| `task build:debug` | macOS 普通 Debug 应用：`target/debug/bundle/macos/` |
| `task build:release` | macOS 普通 Release 应用：`target/release/bundle/macos/` |
| `task build:experimental` | macOS 并发候选 Debug 应用：`target/experimental/debug/bundle/macos/` |
| `task install:macos` | 先构建普通 Release，再安装到 `~/Applications` |
| `task install:macos:debug` | 先构建普通 Debug，再安装 |
| `task install:macos:experimental` | 显式构建并安装并发候选 Debug |

安装目录可通过 `task install:macos INSTALL_DIR="/Applications"` 指定；需要对该目录有写权限，任务不使用 sudo。每次安装都会先构建对应变体，不会把上次残留的实验包误作普通包。普通与实验构建仍共用前端输出目录，请勿并行执行构建或安装任务。

安装脚本检查应用标识和入口，发现任何名为 `cataclysm-hub` 的运行进程时拒绝替换；不会强杀、自动启动应用或迁移元数据。新包在目标目录内暂存，复制失败不动旧包；旧包以 `Cataclysm Hub.previous-<随机标识>.app` 保留，发布失败尝试恢复旧路径。安装期间请保持应用关闭；进程检查不提供对外部启动的原子锁，也不替代签名/公证认证。

实验构建仅启用固定 H/I QA 候选，不代表任意游戏版本可并发或真实验收已通过。需要隔离 QA 元数据时使用 Debug 构建及 `CATACLYSM_HUB_DATA_DIR`；Release 忽略该变量。实验包与普通包使用相同应用标识，安装实验包会替换同目录下普通包，旧包仍保留；可将 `INSTALL_DIR` 指向单独测试目录。

## 本地开发

需要 Node.js 24、npm 11、Rust 1.99.1 及对应平台的 Tauri 系统依赖。macOS 需要 Xcode；当前实际验证以本机 macOS Apple Silicon 为准。

```sh
npm ci
npm run desktop dev
```

仅预览界面使用 `npm run dev`；浏览器不能选择本地目录或启动程序，不包含模拟游戏数据。

```sh
npm run check                     # 格式、TypeScript、组件测试和前端构建
cargo test -p hub-core --locked    # 文件路径、数据库、真实合成进程集成测试
cargo clippy -p hub-core --all-targets --locked -- -D warnings
npm run bindings                  # 从 Rust DTO 生成 TypeScript 类型
npm run desktop -- build --debug --bundles app
```

macOS 打包命令生成 `target/debug/bundle/macos/Cataclysm Hub.app`。开发预览包不代表完成正式签名、公证或兼容认证。

调试构建可通过 `CATACLYSM_HUB_DATA_DIR` 隔离元数据；正式 Release 忽略该变量。新工作区根目录默认采用平台应用本地数据位置，与元数据分离；macOS、Windows、Linux 的约定见 [目录设计](docs/design/platform-settings-instance-workflow.md)。目前原生实际验证范围以 macOS 为准。

进入“世界与角色”后可扫描已配置的存档根目录。所有子目录目前都只视为候选，不解析或合并角色身份。扫描上限为 20,000 个条目、32 层目录；达到限制或遇到无法读取/无损表示的名称会显示不完整报告。链接只列出，不读取目标。扫描与管理器启动操作互斥，扫描结果不代表已冻结的数据快照。

元数据已升级至 schema 16。打开旧工作区前会在元数据目录创建并校验 `metadata-v{旧版本}-{uuid}.sqlite` 备份，再事务执行迁移。该文件是元数据保护副本，不是游戏存档备份。

### 获取游戏与资源

“游戏库 → 获取游戏”从 DDA、BN、TLG、EOD、TISH 的官方仓库读取近期发布及最新非预发布版本。首次启动自动尝试同步，之后点击“更新版本”更新；离线失败保留缓存，不自动重试。“模组与声音 → 下载资源”提供 CC-Sounds、Kenan DDA 历史包及 BN 固定提交包。下载支持进度、取消、校验和原始包删除；解包后仍需通过已有入口登记游戏或单个资源目录，再配置实例。详见 [上游目录与下载说明](docs/design/upstream-catalog-downloads.md)。

## 独立完整备份

进入“存档与备份 → 独立备份”，选择工作区存档根目录或关联实例，预览文件范围，关闭游戏并确认尽力快照风险后创建。应用先复制和哈希比对源文件，再写 TAR+Zstandard，回读校验通过后发布 `{backup_id}/archive.tar.zst` 与 `receipt.json`。源文件保持不变。所有新备份的一致性标识为 best_effort，文件完整性通过不代表游戏语义一致。

当前上限为 20,000 个条目、32 层目录、64 GiB 普通文件、8 MiB 清单。链接、特殊文件、Unix 硬链接或无法完整读取的范围会中止，不会静默丢弃文件。失败/取消可能保留带任务标识的 `.partial-{task_id}` 目录；它不会计为有效备份，也不会自动删除。

以下工具可在没有原数据库或 Git 仓库时独立校验备份目录，不执行恢复或解包写入：

```sh
cargo run -p hub-core --bin verify-backup -- /path/to/backup-id
```

`receipt.json` 丢失时，工具仍可依照归档内部清单逐文件校验，并返回 `receipt_present: false`。哈希不证明发布者身份。当前仅支持本应用生成的 v1 完整文件集合格式（工作区或实例来源）；跨平台恢复、ACL/xattr 和游戏加载兼容性尚未验证。

### 备份名称与保留标记

备份卡的“编辑名称与保留锁”可设置名称、多行备注和本机保留锁，取消不保存。名称、备注和锁存入本机元数据，不修改归档内容、UUID 目录或校验事实；外置备份单独搬到另一台机器不会自动携带这些标注。编辑采用修订号检查，旧草稿不能覆盖新信息。

当前提供保留规则只读预览，可模拟最近份数及 UTC 日/周窗口，展示命名、锁定、恢复引用和历史校验保底等原因；不读取介质、不执行清理或删除。版本/存档环境关联尚未验证，规则外候选不等于允许删除。保留锁不限制操作系统文件操作；后续清理仍需后端检查命名/锁定、最后有效副本与介质情况。实现边界见 [备份标注设计](docs/design/backup-details-implementation.md)。

## 恢复到全新目录

桌面在“独立备份”选择某份归档的“恢复到新目录”，通过本机选择器选父目录。预览展示将新建的 restored-{uuid} 完整路径、容量、归档摘要和风险；关闭相关游戏并确认后才开始写入。任务支持阶段查询与取消，重启后中断任务不自动重放，成功也不会自动切换当前存档。

仅支持本应用完整文件集合 v1 归档。目标必须尚不存在，连已有空目录也不会写入。独立命令行执行：

```sh
cargo run -p hub-core --bin restore-backup -- /path/to/backup-id /path/to/new-recovery --confirm-new-directory
```

恢复文件位于 `new-recovery/data/`。工具先校验整个归档，再受控解包，最后重新读取目标文件核对路径集合、类型、大小与 SHA-256。成功返回 `state: verified` 并写入 `restore-verification.json`；该状态仅表示恢复字节与清单一致，不代表游戏可加载或兼容。

失败保留 `RESTORE_INCOMPLETE.json` 和可能的部分文件，不会自动清理或重放；不要把未完成目录作为存档使用。真实磁盘故障可能使标记写入也失败，必须结合命令退出状态判断。工具不切换当前存档，不覆盖既有目录，也不依赖原应用数据库。桌面使用同一恢复核心，任务与备份、扫描及游戏启动互斥。详细流程与限制见 [新目录恢复设计](docs/design/new-directory-restore-implementation.md)。

### 只读检查已恢复目录

桌面恢复任务下可直接选择“检查已恢复目录”，查看持久检查结果、时间、原标记及摘要；检查可取消，与其他工作区任务互斥。原恢复状态保持历史结论，新的检查失败会单独展示，不用旧成功记录掩盖变化。

中断后或日后需要确认恢复文件时，也可在关闭外部写入者后独立检查，不要求原应用数据库存在：

```sh
cargo run -p hub-core --bin verify-restored -- /path/to/backup-id /path/to/recovery-container
```

第二个参数是包含 data/ 的恢复容器。工具重新验证源归档，再逐项核对恢复载荷的路径、类型、大小和 SHA-256；不会写文件、修补标记、改判任务或再次恢复。输出中的 `verification.state=verified` 只代表本次观测的字节匹配，`incomplete_marker_present` 和 `historical_report_present` 分别报告原标记是否存在，不能据此宣称原任务成功或游戏兼容。文件变化、缺失、额外条目、类型不符或不可完整读取都会失败。
