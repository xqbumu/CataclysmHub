# 多版本并发验证方案审查

日期：2026-10-28。范围：USR-001、real-game-binding-acceptance.md 的验收步骤、现有占用模型及 H/I 实测证据。本次只审查方案，没有运行新的游戏实验或修改并发代码。

复审结论：现有方案已经包含真实双开、范围冲突与故障验收，不能概括为仅适合单实例探索。其执行判据仍需细化；此前“2 项 P1、3 项 P2”的定级撤回，以下为修正后的方案建议，并非已确认的产品代码缺陷。保留独立完整安装、完整实例根、直接进程监测与未知范围保守阻断的方向；补齐下列可执行判据后，再实现最小范围准入。不要求先建设通用沙箱、分布式租约或全部版本兼容系统。

## 发现

### [用例细化] 世界共享状态的拒绝用例

位置：[验收步骤 3–5](real-game-binding-acceptance.md#验收顺序)。需求已要求拒绝同世界，但方案只有泛称“共享”负例，没有明确“同一世界的两个不同角色也必须拒绝”。若按角色 .sav 文件分锁，会放行同时写世界地图、派系/NPC/任务等共享状态的两个进程。程序路径或角色名不同不能消除此冲突。

固定 I-1 源码的 save_factions_missions_npcs 写 world_base_save_path 下主状态，save_maps 写地图/大地图/mapbuffer；game::save 将其与玩家文件依次保存。[上游保存实现](https://github.com/CleverRaven/Cataclysm-DDA/blob/7b2efa5cea38e4d4d97dd0e63b28b9148623da59/src/game.cpp#L3480-L3544)。

修订：首版采用完整安装包 + 完整实例数据根为独占范围，不细分角色锁。加入“同世界不同角色”“不同世界但共享配置/user 根”“链接或硬链接共享可写文件”拒绝用例；同名世界位于不同独立实例则应允许。负例先在 Hub 准入处验证拒绝，不能实际并发损坏样本世界来证明风险。

### [用例细化] 将既有备份约束落实到并发测试

位置：步骤 5 的“备份/恢复只与涉及范围冲突”。结合 instance-backup.md，已有设计明确完整实例根、读取占用、活动游戏全局阻断和 best_effort；故不能认定设计缺失这些保护。需要在未来按范围准入时补成读写冲突与无关操作放行的回归断言。CDDA 保存分多步、多个文件；逐文件校验通过不能证明它们来自同一个游戏状态。[game::save](https://github.com/CleverRaven/Cataclysm-DDA/blob/7b2efa5cea38e4d4d97dd0e63b28b9148623da59/src/game.cpp#L3653-L3686)。

修订：A/B 同时运行时，A 数据根的备份及写入性恢复/复制/清理应因 A 写入声明被拒绝。A 正常结束且进程归属已确认后，允许备份 A、B 继续游玩；恢复至新空目录并用 A 的原版本/资源实际加载验证，保持原件。没有游戏协作冻结机制前，不把运行中备份标为语义一致。未知退出继续保护，不以 exit_code=0 单独证明保存成功。

### [覆盖建议] 按独立写入路径选择游戏场景

位置：步骤 3、4 及现有 QA 证据。现有样本覆盖默认场景和温缓存，未强制触发自动保存、地图状态持久化、死亡后的墓地/纪念写入与冷缓存生成。仅能操作后保存读档，可能遗漏这些分支的共享路径。I-1 自动保存同时受操作计数与墙钟间隔影响，空等时间不保证触发；死亡归档会移动/删除角色相关文件。[自动保存](https://github.com/CleverRaven/Cataclysm-DDA/blob/7b2efa5cea38e4d4d97dd0e63b28b9148623da59/src/game.cpp#L13473-L13535)、[墓地迁移](https://github.com/CleverRaven/Cataclysm-DDA/blob/7b2efa5cea38e4d4d97dd0e63b28b9148623da59/src/game.cpp#L3164-L3199)。

修订：各版本单独补一次冷缓存启动、一次温缓存重启；记录实际选项、执行足够回合并核实自动保存产物；移动/拾取并改变地图物品或门状态，跨进程读档确认角色位置、物品、地图及时间。专用可丢弃角色执行死亡归档，记录墓地、纪念及版本适用的成就写入，B 继续保存和重载。核心数据组合先做；承诺支持模组/音效/图块包时增加一个明确资源组合，未测试组合继续未验证，不要求穷举所有模组。死亡用例不能针对玩家存档。

### [执行判据缺口] 活动 B 的文件变化缺少归因判据

位置：步骤 4 与 snapshot/diff 示例。B 保持运行时可能自行产生合法日志或保存写入；把 B 任何变化直接判为 A 越界会产生误报，反之将 A/B 都设为允许变化又无法发现交叉污染。快照本身也不具备进程归因。

修订：分两组实验。隔离组让 B 停在已确认静止的菜单或暂停状态，先做同长度无 A 操作的基线；有自写入则记录并用写入跟踪或单独对照解释，不忽略整个 B 范围。压力组让两者交替推进并近同时保存，允许各自预期变化，通过不同角色/世界标记与跨进程读档检查污染；不能仅凭 diff 返回 0 宣告隔离通过。任一无法解释的跨实例写入阻止发布。

### [执行判据缺口] 候选实现与支持范围需要明确

位置：步骤 1、5、6 及“当前 Hub 操作”。方案说摘要/适配器变化使证据失效，但没有规定哪份证据可授权哪种启动；当前 binding_verified 恒 false、全局互斥，与“先由 Hub 双开验收”之间仍缺少实现/测试阶段分界。顶部 Resources v1 操作与后文原生入口 QA 结果也不是同一条支持路径。

修订：先把本机 H/I 的修改版 QA 包作为实验候选，记录其入口与 plist 调整；它们不能直接定义面向用户的首发支持范围。首发范围须具备可重复获得的安装与启动流程。原始发行包适配未完成可标为产品支持限制，但无需阻止候选调度实现的测试。为候选实现写清服务端准入条件及可重复集成测试，再在候选实现上做 Hub 双开；不通过手工改数据库信任位或删生产全局锁取得验收。证据记录程序、资源组合、适配器、路径及平台范围；摘要/物理身份/启动参数变化或未知进程一律回到保守阻断。只需最小证据关联，不必先造通用认证平台。

## 建议的最小执行矩阵

| 用例 | 实际操作 | 必须断言 |
|---|---|---|
| G1 单版本基线 | H/I 各冷启动与温重启；手动/自动保存；改角色与地图状态后跨进程加载 | 状态恢复、写入范围可解释、无另一实例变化 |
| G2 双开交叉 | Hub 内 A/B 同时进入不同世界，交替及近同时保存，再分别跨进程重载 | 两个真实会话；各自状态正确；无污染 |
| G3 退出与死亡 | 正常退出 A；另用可丢弃 A 角色触发死亡归档 | B 仍能操作、保存及重载；B 保护不释放 |
| G4 共享负例 | 同世界不同角色、共享 user/config/包缓存、目录别名和可写文件硬链接 | 产生第二个游戏进程前拒绝；同名但物理独立世界不误拒绝 |
| G5 文件任务 | B 运行；A 运行时请求备份 A，A 结束后备份/新目录恢复并原版本加载 | 活动 A 冲突；结束后允许不相关操作；B 保持受保护 |
| G6 故障 | Hub 重启/强杀、单游戏异常退出、目录替换/断盘、终态审计失败；PID 复用用合成夹具 | 未知归属不误释放；另一实例继续保护；不承诺崩溃保存无损 |

真实游戏承担玩法/存档语义验收；合成程序承担可控的 PID/子进程/审计失败注入，两者证据分开。每个单元须有明确支持组合、前置状态、实际操作、会话/进程身份、保存前后语义标记、范围差异和结论。快照与 GUI 截图不能单独证明完整 OS 写入边界。

## 范围限制

并发意味着独立环境同时游玩，不意味着 H 存档能由 I 升级后再降级加载。首版固定各世界所属版本/资源，不自动换绑；跨版本加载只在副本上进行，归入后续迁移验收。世界删除/重置也会改变整个世界；若游戏内提供该操作，专用测试世界的验证需证明另一实例不受影响，不新增 Hub 删除能力。

现有 H/I 顺序游玩及外部启动器双开证据保留有效，但不能代替 G2 的 Hub 调度结果。此审查未判定产品已支持并发。


## 对上述结论的复审与收敛

本节优先于上文未展开的建议。复核依据为 USR-001 第 12、20 行的同世界拒绝要求，instance-backup.md 的全局冲突与 best_effort 契约，以及 resource_claims.rs 已有读写声明。前次依据 I-1 源码说明游戏风险有效，但不能据此认定 H 的全部细节相同，也不能将未来假设的角色锁缺陷列为当前 P1。

1. **撤回两项 P1。** “同世界不同角色”和“运行中备份”是已有要求的具体化。当前全局锁并未放行这些危险行为；没有证据表明现有代码违反要求。
2. **覆盖按写入路径选取。** I-1 autosave 调用 quicksave，后者进入既有 save 流程；自动保存值得覆盖，但不必把每种保存触发方式都当作独立架构前置。先验证角色和世界共享状态实际恢复、冷缓存写入；墓地/纪念等额外路径用一次代表性专用夹具覆盖。完整 user 根纳入范围后，无须逐项解锁每个玩法功能或穷举模组组合。死亡/世界重置属于补充覆盖，不全部阻塞首个候选调度切片。
3. **修正观察结论。** B 菜单静止基线只能帮助排查，不能证明 A 没有写 B；时间相近的对照也不能做确定归因。该对照不能替代两个实例同时进入世界的主用例。需要因果归因时采集实际进程及后代的写入记录；采集不可用时，仅报告声明范围差异与读档结果，结论保留“未观察到”，不能称完整隔离已证明。尚无法解释的 B 变化是待调查结果，不直接断言 A 越界。
4. **缩小故障与平台承诺。** 候选首版仅允许已明确生命周期的直接进程路径；不支持的包装器/子进程接管应拒绝或保守保留未知占用，无须先实现通用进程树接管。Hub 无法阻止所有外部程序或另一独立工作区手工打开同一数据；支持边界需说明，不能把内部范围锁当成 OS 强制保护。
5. **避免把资源组合摘要做成全目录不变证明。** 安装缓存、实例存档和配置正常写入会变化；不可把这些合法变化统一视为证据失效。程序/静态资源/适配器身份与运行数据分别处理，路径移动重新检查物理边界，未知变化再阻断。
6. **备份按实际源/目标判断。** 读取活动 A 的数据应冲突；从既有不可变归档恢复到与 A/B 都无关的新目录，不应仅因归档记录关联 A 就阻断。是否还受共享备份目录写入影响，要按实际声明判断。

最小实施顺序：先明确候选支持路径与完整包/实例根读写冲突规则；用合成用例验证独立范围准入、共享拒绝、终态失败与重启未知保护；随后在候选版本上做 Hub 内 H/I 真正双开、交叉保存及跨进程重载、A 退出而 B 继续游玩；最后补代表性异常写入路径及不相关备份操作。跨版本升级/降级兼容保持独立验收，不扩大本特性的完成条件。

本轮仅修正文档，没有新的真实游戏实验；既有双开与顺序验收证据不因审查措辞修正而被否定。
