# 真实游戏配置应用与回滚验收

日期：2026-10-29。状态：流程与离线证据检查工具已准备；真实游戏执行待人工完成。

## 验收范围与参与方式

游戏内按键、设置观察、创建实验世界、保存及退出均由用户完成。开发代理不向正在游玩的游戏发送按键，不自动结束游戏，不替换当前桌面应用。只使用明确指定的可丢弃独立实例，记录精确游戏构建、包来源／本体摘要、Hub 提交与构建特性、启动参数方案、资源组合和实例路径。已有本机 H/I QA 包的历史结果不继承为本轮通过。

本流程分别验证文件发布／回滚、游戏读取设置、实际声音、新世界默认组合；不把其中一项作为其他项的证据。真实多版本并发继续遵循[独立验收契约](real-game-binding-acceptance.md)。本轮单文件操作需要全部 Hub 会话及文件任务结束；还要人工确认没有外部游戏进程写入目标。

## 0. 环境准备

1. 明确实例 A、安装 A、静止对照实例 B、保护哨兵目录及范围外证据目录。完整安装包和完整实例根不得重叠，不能拿不同世界目录代替独立实例根。备份根、Hub 元数据和证据输出均在被观察目录之外。
2. 确认使用包含单文件应用与回滚功能的 Hub 构建；记录实际提交，不以源码已提交推断正在运行的应用已更新。现有桌面应用若正在使用，先完成用户操作再另行安排构建切换。
3. 在游戏自身界面生成真实配置并正常退出；若目标文件缺失或声音字段未声明，先按游戏本身流程生成，不捏造默认文件以绕过拒绝。
4. 只读报告确认候选资源范围与诊断。准备应用会保守阻止不完整扫描或未解决的诊断；遇到拒绝先记录原因，不手工修改信任位、删除保护记录或关闭检查。
5. 将本轮原始日志与截图存于证据目录，复制[人工记录模板](content-config-manual-record.template.md)填写。未执行项目保留“未执行”，不能以推测填写通过。

## 1. 游戏关闭时的单文件循环

该段只验证文件字节，三次快照之间不得启动游戏。先完成保护备份并检查任务成功，再采基线；否则新归档变化会混入观察范围。

1. A、B 及外部写入者均退出。一次只选 options 或新世界默认模组配置。生成后端草稿、创建保护备份，记录备份 ID、原 SHA-256、期望应用后 SHA-256。
2. 使用目录观察工具采 `before.json`。范围至少包括完整实例 A、安装 A、静止实例 B、保护哨兵。下列路径须替换为本次真实独立测试目录：

   ```sh
   python3 scripts/acceptance/observe_scopes.py snapshot \
     --scope instance-a=/absolute/qa/instance-a \
     --scope install-a=/absolute/qa/game-a \
     --scope instance-b=/absolute/qa/instance-b \
     --scope protected=/absolute/qa/protected \
     --output /absolute/qa/evidence/before.json
   ```

3. 选择同实例保护归档，重新准备单文件应用，核对后明确确认；等待记录变为 applied。记录应用 ID、计划目标和摘要。保持游戏关闭，使用相同范围采 `applied.json`。
4. 在该原始应用记录上预览回滚，确认恢复原字节。等待新的关联记录完成，记录 rollback_of、回滚 ID 与摘要；仍不启动游戏，采 `rolled-back.json`。
5. 执行检查（SHA-256 从本次实际确认计划复制）：

   ```sh
   python3 scripts/acceptance/check_config_cycle.py \
     --before /absolute/qa/evidence/before.json \
     --applied /absolute/qa/evidence/applied.json \
     --rolled-back /absolute/qa/evidence/rolled-back.json \
     --scope instance-a --path config/options.json \
     --expected-applied-sha256 'REPLACE_WITH_PLAN_SHA256' \
     --output /absolute/qa/evidence/config-cycle.json
   ```

   将 `REPLACE_WITH_PLAN_SHA256` 替换为本次计划中的 64 位小写摘要；占位符原样运行会被工具拒绝。默认模组轮次改用 `config/user-default-mods.json`，且使用另一组新证据文件。

检查会允许目标文件 inode 因原子替换而变化，但要求目标摘要符合计划、回滚大小与摘要符合原字节、普通权限一致。任何其他文件／目录变化、根身份变化、外部链接／特殊文件、缺失文件或覆盖范围缺失均阻止通过。遗留临时文件不加入豁免。

`file_cycle_check=matched` 只表示三份输入快照符合这些字节条件，不认证截图真实性、进程已退出、操作归因、实际加载或范围外无写入。工具不校验 Hub 的操作日志签名；还须人工核对任务和备份 ID，快照间产生又删除的短暂写入也可能遗漏。

## 2. 游戏读取声音设置（另起基线）

1. 为可丢弃 A 重新采基线并创建保护备份，使用已经可见且元数据无歧义的声音包。分别记录声音包 ID、VIEW、声音开关原值与拟值。只有开关变化不等同声音包安装成功。
2. 由 Hub 明确确认单文件应用，采“启动前已应用”快照。用户启动同一实例，核对游戏内包选择、音量及开关；记录实际设备、系统静音状态和可重复的声音触发事件，由用户说明是否确实听到音效。不能仅凭文件值或菜单截图填写“声音播放通过”。
3. 正常退出并确认进程结束后再采快照，读取配置报告与应用记录核对当前摘要。
4. 若游戏重新序列化了配置，即使显示设置相同，文件也可能不再匹配原应用结果。这时回滚预览应拒绝；记录为“游戏改写后保护拒绝”，不要删除记录或改摘要来强制回滚。需要另起保护基线并重新设计后续操作。
5. 若当前字节仍与应用结果相同，可单独确认回滚并核对原字节。之后再次启动游戏检查恢复的设置，作为单独人工观察；第二次退出后的游戏改写不抹除此前回滚字节证据。

## 3. 新世界默认组合（与已有世界分开）

1. 使用游戏已生成的默认组合文件，只选择本构建候选范围内可见且依赖清楚的组合。记录顺序、依赖与具体版本，建立保护备份后单文件应用。
2. 用户进入新世界创建界面，观察初始模组列表是否反映预期；创建专用可丢弃世界，完成加载并正常退出。记录世界名、实际列表与任何报错，不能只以 JSON 可解析判断加载成功。
3. 已有世界的 `save/<world>/mods.json` 应独立观测；不要求游戏运行期间整个实例一字不变，也不能把旧世界未改变当成新世界加载成功。
4. 退出后检查游戏是否改写默认组合文件；若变化则执行与声音测试相同的拒绝处理。跨版本复用已有世界或删除旧世界模组不属于本轮。

## 4. 故障与结论

真实强杀、断盘和未知进程实验只在专门可丢弃实例另行安排，不在用户日常游戏中执行。本轮合成回归已覆盖审计失败、中断核对、重启不重放与第三种内容拒绝；合成结果不替代真实平台故障认证。

逐项记录：静止字节循环、声音设置读取、实际声音、新世界默认列表、实际加载、游戏退出后的序列化行为、回滚拒绝／成功、其他范围变化和未覆盖项。单项不通过或未执行保留其独立状态；不自动提升 binding_verified 或 concurrency_accepted。
