## 1. 执行摘要与产品愿景

Cataclysm Hub 是面向 Cataclysm 系列生存游戏的跨平台桌面管理工具。它把游戏安装与版本、mods、soundpacks、tilesets、字体、环境档案、世界与角色存档、Git 历史、独立完整备份、恢复验证和操作日志整合到统一界面。

首要目标环境为 macOS Apple Silicon 上的 Cataclysm: Dark Days Ahead（CDDA）0.I Ito 与 MSXotto+ 图块资源组合。架构必须可扩展至 Windows 与 Linux，并通过适配器机制逐步支持经验证的 CDDA 版本及相关分支。

产品最重要的差异化不是单纯启动器，而是对存档安全的明确承诺：以世界为默认一致性单元，尽可能在游戏稳定退出后创建可恢复检查点；Git 历史和独立完整备份相互补充；自动 commit 说明可由存档差异生成；任何无法确认的行为和兼容性都必须诚实标注。

### 1.1 产品愿景

让玩家可以安全地管理多个游戏版本、资源组合和生存世界；在升级、安装资源或实验新玩法之前创建可验证的回滚点，并能理解每次存档变化大致发生了什么。

### 1.2 产品成功指标

| 指标 | 目标/度量方式 | 首发目标 |
|---|---|---|
| 备份可验证率 | 成功创建且 SHA-256/清单验证通过的备份比例 | ≥ 99.5%（排除用户主动取消与磁盘不足） |
| 恢复演练成功率 | 在受支持测试环境中，备份恢复后文件清单与目标快照一致 | 100% 的发布阻断测试通过 |
| 自动检查点可靠性 | 监控触发后产生有效快照或明确失败状态的比例 | ≥ 99% 的可复现测试场景 |
| 数据丢失事件 | 由 Cataclysm Hub 自身操作导致的已确认数据丢失 | 0 个已知发布阻断缺陷 |
| 摘要可解释性 | 每条结构化摘要都能追溯到检测结果 | 100% |
| 跨平台核心测试 | 三平台核心安装、检查点、备份、恢复测试 | 每个正式版本执行 |
| 离线可用性 | 无网络时启动、查看本地存档、Git、备份和恢复 | 必须支持 |

## 2. 背景、问题与目标

### 2.1 现状问题

- 游戏版本、分支和资源包往往分散安装，难以准确追踪某个世界对应的版本与资源组合。
- 世界可能包含多个角色或相互关联的数据；只备份角色文件容易产生不一致恢复。
- 单纯复制目录不便于查看历史差异；单独使用 Git 也不等于拥有经过验证的完整灾难恢复备份。
- 游戏保存过程可能同时改写多个文件，游戏运行期间直接提交会产生不一致快照风险。
- 原始文件 diff 对玩家不友好；用户需要能读懂的摘要，但摘要不能把推断伪装成事实。
- 资源安装、游戏升级、存档迁移和回滚之间缺乏统一的预检查、审计和失败恢复流程。

### 2.2 产品目标

1. 跨平台管理游戏安装、版本、启动参数与已验证的发行资源。
2. 管理 mods、soundpacks、tilesets、字体及其来源、版本、校验和兼容性声明。
3. 发现和组织世界/角色关系，默认以世界为 Git 与完整备份的核心一致性单元。
4. 提供可审计的 Git 检查点和可独立恢复的完整归档备份。
5. 基于文件差异与结构化存档差异生成 commit 摘要，必要时提供可选 AI 润色。
6. 在恢复、升级、迁移、清理等高风险操作前进行预览、保护和明确确认。
7. 允许离线工作；联网功能仅用于发现发行、下载资源或用户主动启用的功能。

### 2.3 非目标

- 不修改或重新分发 CDDA 游戏本体，除非未来明确采用合规的发行下载机制。
- 不承诺不同游戏版本、分支或模组组合之间的存档兼容性。
- 不将未经验证的角色文件跨世界移植作为默认能力。
- 首发不提供云端存档同步、多人协作或在线分享服务；未来功能必须单独评估隐私与冲突解决。
- 不把 AI 生成的行为叙述当作权威游戏事件日志。
- 不要求玩家安装 Spark、服务端或其他与管理器无关的运行时。

### 4.1 用户故事

- 作为玩家，我希望每个世界都有独立的历史和备份，以免一个世界的恢复操作影响其他世界。
- 作为玩家，我希望自动检查点能用自然语言说明发生了哪些可确认的变化。
- 作为玩家，我希望在游戏运行时不产生被误认为一致的检查点。
- 作为玩家，我希望在删除、覆盖、迁移前看到影响范围，并有可恢复的保护副本。
- 作为测试者，我希望知道某个世界由哪个游戏版本、资源版本和启动参数运行。
- 作为离线用户，我希望不连接网络仍能完成本地存档、Git、备份与恢复。

## 6. 产品原则与关键决策

- **数据安全优先：** 任何自动化都不能凌驾于可恢复性之上。
- **世界优先：** 默认以完整世界及其全部角色/相关数据作为一致性备份和恢复单位。
- **双层保护：** Git 历史与独立完整备份职责不同，不能互相替代。
- **离线优先：** 本地管理能力不依赖云服务。
- **渐进式识别：** 先安全地保存原始文件，再解析已知字段；未知字段不得丢弃。
- **可追溯摘要：** 每条摘要必须对应可验证的文件或结构化差异。
- **兼容性透明：** 明确区分已测试、推测兼容、未验证和不兼容。
- **非破坏式迁移：** 源数据默认只读，迁移完成并验证前不删除源数据。
- **用户控制：** 自动备份频率、保留策略、摘要语言、联网与遥测均可配置。

|---|---|---|

| GIT-006 | MUST | 恢复历史前创建保护检查点或完整备份，并展示回滚范围。 |
| GIT-007 | SHOULD | 支持命名标签，例如“升级前”“重要基地完成”“长期存档”。 |
| GIT-008 | MUST | 提供仓库健康检查、对象完整性检查、磁盘空间预警和安全的维护入口。 |
| GIT-009 | MUST | 不得自动执行破坏性 Git 清理或历史重写；必须有显式确认和保护流程。 |

### 7.5 存档差异摘要与 commit 文案

| ID | 优先级 | 需求 |
|---|---|---|
| COMMIT-001 | MUST | 自动检查点生成可读 commit subject；默认使用中文，允许配置语言。 |
| COMMIT-002 | MUST | 首版至少生成文件级摘要：新增/修改/删除文件数、主要路径类别和差异规模。 |
| COMMIT-003 | MUST | 对经过版本验证的存档格式解析角色/世界结构化字段，并生成前后状态差异。 |
| COMMIT-004 | MUST | 摘要区分事实、推断与未知；不能把推测的探索/战斗/制作行为写成确定事件。 |
| COMMIT-005 | MUST | 结构化解析失败时退回文件级摘要，且不阻断 Git 提交或完整备份。 |
| COMMIT-006 | MUST | 每条结构化摘要可追溯到解析器版本、游戏版本和变更类别。 |
| COMMIT-007 | SHOULD | 用户可在提交前编辑标题和正文，或关闭自然语言摘要。 |
| COMMIT-008 | SHOULD | 可选 AI 润色只接收最小化结构化报告；默认不上传原始存档。 |
| COMMIT-009 | MUST | AI 不可用、超时或返回无效文本时，使用确定性模板完成提交。 |
| COMMIT-010 | MUST | 摘要生成器不得决定纳入哪些文件；文件纳入范围由备份/检查点策略决定。 |

### 7.6 文件监控与稳定性判定

| ID | 优先级 | 需求 |
|---|---|---|
| WATCH-001 | MUST | 监控存档相关目录变更，并对事件进行去抖和批处理。 |
| WATCH-002 | MUST | 文件监控事件只触发候选检查点，不直接证明存档已一致。 |
| WATCH-003 | MUST | 游戏运行时默认不创建标记为“稳定”的检查点。 |
| WATCH-004 | MUST | 进程退出后，等待配置的静默窗口并检查文件大小/修改时间是否稳定。 |
| WATCH-005 | MUST | 若检测到文件持续变化、锁定或进程仍运行，延迟快照并解释原因。 |
| WATCH-006 | SHOULD | 支持用户手动请求“尽力快照”，并醒目标注一致性风险。 |
| WATCH-007 | MUST | 监控失效、权限不足或目录不可访问时，展示告警且不得假装正在监控。 |

## 8. 存档、世界绑定与一致性模型

### 8.1 一致性单元

默认一致性单元为一个世界及其所有可识别的角色和相关世界状态。世界边界必须来自当前版本实际存档布局和解析器规则，不能假设所有 CDDA 版本均采用相同目录结构。若无法确定某个文件属于哪个世界，应将其列为共享/未知数据，并在备份计划中明确展示。

### 8.2 角色恢复策略

- 默认允许恢复整个世界或整个存档根目录。
- 默认禁止将角色文件直接恢复到另一个世界。
- 单角色导出可以作为高级功能，但应导出到隔离目录并明确标注不保证可直接导入或与目标世界一致。
- 未来若提供角色迁移，必须有独立迁移器、兼容性检测、完整源备份和明确的风险确认；不得伪装成普通恢复。

### 8.3 一致性状态机

| 状态 | 含义 | 允许动作 |
|---|---|---|
| `Watching` | 监听存档变化 | 记录变更、等待触发条件 |
| `GameRunning` | 游戏进程运行中 | 只记录变化；不创建权威稳定检查点 |
| `PendingQuiescence` | 进程已退出，等待文件静默 | 执行静默窗口和文件稳定检查 |
| `Validating` | 校验路径、文件可读性与世界边界 | 通过后进入快照阶段 |
| `Snapshotting` | 创建 Git 检查点/完整归档 | 显示进度；写入临时目标 |
| `Verifying` | 校验仓库/归档完整性 | 通过后标记为 verified |
| `Verified` | 检查点完成且验证通过 | 允许用于常规恢复 |
| `BestEffort` | 用户要求或特殊情况下创建的尽力快照 | 明确警告，不作为权威稳定点 |
| `Failed` | 任务失败 | 保留诊断信息；不得标记成功 |

### 8.4 一致性与崩溃恢复要求

- 创建归档时先写临时文件，校验通过后再原子替换/发布最终文件（平台能力允许时）。
- 任务状态写入数据库；应用重启后扫描临时文件并判断可恢复、可删除或需人工处理。
- 恢复操作必须先验证源备份清单、目标路径和可用磁盘空间。
- 恢复完成后再次计算文件清单/摘要，并记录恢复来源与结果。
- 不得仅凭“游戏进程已退出”认定存档稳定；还需静默窗口和文件稳定性检查。

## 9. Git 历史与智能 commit 摘要

### 9.1 摘要管线

1. 获取上一个已验证检查点和当前候选快照的文件清单。
2. 计算文件增删改、大小变化、哈希变化和目录类别统计。
3. 调用与游戏版本匹配的结构化解析器，对已知字段生成语义差异。
4. 将事实与推断分开保存，附加置信度、解析器版本和原始证据引用。
5. 使用确定性模板生成 subject/body；用户可编辑后提交。
6. 可选调用 AI 进行语言润色，但 AI 不能修改结构化事实或文件清单。

### 9.2 摘要分类

| 分类 | 示例 | 规则 |
|---|---|---|
| 文件事实 | 修改 127 个文件，新增 3 个文件 | 可由文件清单直接计算。 |
| 角色状态 | 角色位置字段变化、物品数据变化 | 仅在解析器可靠识别字段时生成。 |
| 世界状态 | 世界元数据或地图区块变化 | 说明数据变化，不直接推断玩家行为。 |
| 行为推断 | 可能探索了新区域 | 必须标注“可能/推测”，且可在设置中关闭。 |
| 未知变化 | 若干二进制/未知格式文件变化 | 如实展示，不进行猜测性叙述。 |

### 9.3 示例 commit

```text
存档更新：Riverside 世界状态变化

- 修改 127 个文件，新增 3 个文件
- 角色位置字段发生变化
- 多个地图相关文件发生变化
- 未识别字段保留原样，未进行行为推断

World: Riverside
Checkpoint: automatic
Game: CDDA 0.I Ito
Summary: structured-diff-v1
```

### 9.4 隐私与 AI 摘要

- AI 摘要默认为关闭或明确选择启用，不影响本地模板摘要。
- 默认只发送最小化的结构化变更报告，不发送原始角色数据、地图文件、路径中的个人信息或完整存档。
- 发送前展示提供商、数据类别和请求预览；记录用户授权设置。
- AI 输出必须经过长度、字符、敏感字段和事实约束检查；失败时回退模板。

## 10. 完整备份、校验与恢复

### 10.1 完整备份要求

| ID | 优先级 | 需求 |
|---|---|---|
| BACKUP-001 | MUST | 独立于 Git 仓库生成可单独恢复的完整归档。 |
| BACKUP-002 | MUST | 默认以世界为单位；同时支持整个存档根目录级备份。 |
| BACKUP-003 | MUST | 归档包含文件清单、相对路径、文件大小、SHA-256 和格式版本。 |
| BACKUP-004 | MUST | 建议首发使用 TAR + Zstandard；压缩格式必须版本化且可检测。 |
| BACKUP-005 | MUST | 归档写入临时路径，完成后验证，再发布为正式备份。 |
| BACKUP-006 | MUST | 支持验证归档完整性，不必先覆盖用户现有存档。 |
| BACKUP-007 | MUST | 备份失败必须显示具体原因，例如权限不足、磁盘不足、源文件变化。 |
| BACKUP-008 | MUST | 备份目录默认与源存档目录分离；用户可选择外置磁盘路径。 |
| BACKUP-009 | SHOULD | 支持保留策略：自动检查点、每日、每周和命名检查点分层保留。 |
| BACKUP-010 | MUST | 命名/锁定检查点不因自动清理被删除；最近一次验证成功的备份必须保留。 |
| BACKUP-011 | MUST | 删除备份前展示数量、容量、时间范围和是否为最后一个有效备份。 |

### 10.2 建议默认保留策略

| 类别 | 建议默认值 | 规则 |
|---|---|---|
| 自动检查点 | 最近 7 份 | 可配置；仅删除前需确认策略且确保仍有有效恢复点。 |
| 每日备份 | 14 天 | 保留每天至少一个已验证备份。 |
| 每周备份 | 8 周 | 保留每周至少一个已验证备份。 |
| 命名检查点 | 永久保留 | 用户主动删除前不得自动清理。 |
| 最近验证成功备份 | 至少 1 份 | 任何自动保留策略都不得删除唯一有效备份。 |

> 以上为产品建议默认值，最终应在设置中可调整；实现必须避免保留策略和命名保护规则相互冲突。

### 10.3 备份清单字段

- `backup_id`、`schema_version`、`created_at`、`backup_type`、`consistency_status`。
- `world_id` / `world_alias`（如已识别）、角色清单及识别置信度。
- 游戏分支/版本、操作系统、架构、环境档案引用、解析器版本。
- 相对路径、文件大小、修改时间（可选）、SHA-256。
- 源路径标识（避免不必要地泄露用户名或绝对路径）、文件数量、总字节数。
- 压缩算法/版本、归档摘要、验证结果、创建工具版本。

### 10.4 恢复流程

1. 用户选择世界或存档根目录及一个已验证备份。
2. 执行预检：世界身份、目标路径、版本差异、磁盘空间、权限、备份清单和校验结果。
3. 展示恢复影响：将覆盖/新增/移除的文件、目标世界、关联角色以及兼容性警告。
4. 自动为目标当前状态创建保护备份；若无法保护则默认中止覆盖式恢复。
5. 在隔离临时目录解包，拒绝绝对路径、路径穿越、符号链接滥用和重复路径等危险条目。
6. 验证解包文件与清单一致后，再执行受控替换；支持中断恢复和回滚。
7. 恢复后重新计算校验、更新数据库关联并记录审计日志。
8. 首次启动游戏前提示版本/资源档案差异；不自动保证兼容性。

### 10.5 灾难恢复验收

- 模拟备份过程中应用退出、磁盘写满、源文件变化、权限被撤销。
- 模拟归档截断、清单篡改、单文件校验不匹配和路径穿越条目。
- 模拟恢复过程中应用退出，并验证重启后可安全继续或回滚。
- 恢复到空目录后，验证文件数量、路径、大小和哈希与备份清单一致。
- 验证 Git 仓库丢失时，独立完整备份仍可恢复；完整备份缺失时，Git 历史仍可用于历史回滚（不宣称可替代灾备）。

## 11. 游戏版本、安装与启动

游戏安装与存档数据必须分离。每个世界关联其最后使用的游戏安装、版本和环境档案，但这种关联是记录和风险提示，不代表工具能保证跨版本兼容。

- 支持导入现有游戏目录和用户管理的便携安装。
- 版本信息至少记录游戏名称、分支、版本字符串、平台架构、可执行文件路径和来源。
- 更新前生成世界检查点并建议独立完整备份；允许用户拒绝更新。
- 旧安装被世界引用时，不得自动删除；提供引用关系与清理预览。
- 游戏进程启动时记录启动时间、安装标识和关联世界（若能识别）。
- 支持稳定版、实验版等通道的概念，但具体通道取决于上游实际发行机制。

## 12. Mods、音效、图块集与字体

### 12.1 通用资源模型

- 每个资源包记录名称、类别、版本/修订、来源、安装路径、许可证信息（可得时）、校验摘要和兼容性状态。
- 支持导入本地资源包；远端目录/下载功能必须显示来源与下载资产信息。
- 安装、启用、禁用、升级或删除资源前，展示影响范围，并建议对相关世界创建保护点。
- 资源文件不得静默覆盖用户自定义内容；冲突必须可见。
- 兼容性状态区分：已测试、上游声明兼容、推测兼容、未验证、不兼容。

### 12.2 Mods

| ID | 需求 |
|---|---|
| MOD-001 | 发现本地 mods，并在不破坏原文件的前提下建立索引。 |
| MOD-002 | 支持资源包安装、启用/禁用和按环境档案保存组合。 |
| MOD-003 | 在元数据可用时显示依赖、冲突、版本要求；无法推断时明确标记未知。 |
| MOD-004 | 支持为测试世界建立独立 mod 组合，避免误改主世界配置。 |
| MOD-005 | 对缺失依赖、重复资源 ID 和已知冲突给出可操作提示。 |

### 12.3 Soundpacks、tilesets 与字体

- 音效包管理支持发现、安装、启用、来源记录和配置绑定。
- 图块集管理支持普通地图图块集、远景/Overmap 相关图块集等不同角色；具体类型依据游戏配置实际支持情况实现。
- 字体管理支持发现与选择，记录字体来源、路径和环境档案引用。
- MSXotto+ 作为首要验证资源组合；不得在未验证情况下宣称所有版本均兼容。
- 资源卸载前检查当前档案与世界引用；对仍被引用的资源要求确认或先迁移引用。

## 13. 环境档案、迁移与可复现性

### 13.1 环境档案

环境档案（Environment Profile）记录可复现某个游戏环境所需的元数据，不默认复制或重新分发所有游戏与资源文件。

- 关联游戏安装标识、游戏版本、平台架构、启动参数模板。
- 记录 mods、soundpacks、tilesets、字体的名称、版本/修订、来源和摘要。
- 记录配置文件引用、关键配置摘要及用户选择的显示/渲染设置（在可识别范围内）。
- 支持 JSON 导出；文件格式必须包含 `schema_version` 并允许未来迁移。
- 导入档案时先展示缺失资源、冲突、平台差异与未知字段。

### 13.2 迁移

| ID | 优先级 | 需求 |
|---|---|---|
| MIG-001 | MUST | 支持存档、配置和环境档案的迁移预览。 |
| MIG-002 | MUST | 默认不删除源文件；目标验证通过前源数据保持不变。 |
| MIG-003 | MUST | 跨平台迁移时检查大小写敏感性、路径长度、权限、符号链接和非法文件名。 |
| MIG-004 | MUST | 展示源/目标游戏版本与资源差异，不能静默宣称兼容。 |
| MIG-005 | MUST | 迁移失败时保留源数据和诊断日志，清理目标临时目录前先确认其归属。 |
| MIG-006 | SHOULD | 支持将世界导出到便携归档并附带环境档案。 |

## 14. 数据模型与持久化

本地元数据使用 SQLite；存档原始文件不嵌入数据库。数据库损坏不得导致用户存档本体被删除或不可恢复。数据库 schema 使用版本化迁移，并在应用升级前对元数据数据库做安全备份。

| 实体 | 关键字段/关系 | 用途 |
|---|---|---|
| `GameInstallation` | `id, path, platform, arch, version, branch, checksum, status` | 游戏安装与发行信息。 |
| `GameRelease` | `id, source, version, channel, asset, checksum, published_at` | 发行元数据与下载资产。 |
| `World` | `id, root_path, alias, identity_confidence, status, last_game_install_id` | 世界级管理实体。 |
| `Character` | `id, world_id?, display_name, identity_key?, confidence, metadata` | 角色候选与世界关联；关联允许未知。 |
| `ContentPackage` | `id, type, name, version, source, checksum, compatibility` | mods/音效/图块集/字体。 |
| `EnvironmentProfile` | `id, schema_version, game_install_id, content_refs, config_refs` | 可复现环境。 |
| `SaveRepository` | `id, world_id, git_path, status, last_verified_commit` | 世界的 Git 历史。 |
| `Checkpoint` | `id, world_id, commit_hash, type, consistency, summary, created_at` | 检查点及其摘要。 |
| `BackupArchive` | `id, world_id?, type, path, format, manifest_hash, verification_status` | 独立完整备份。 |
| `BackupManifestEntry` | `backup_id, relative_path, size, sha256, file_type` | 备份内文件清单。 |
| `PlaySession` | `id, game_install_id, world_id?, started_at, ended_at, duration` | 可选游玩统计。 |
| `OperationLog` | `id, operation, target, started_at, finished_at, status, error_code` | 可审计操作记录。 |
| `AppSettings` | `key, value, updated_at` | 本地偏好与策略。 |

### 14.1 数据保留与迁移

- 数据库迁移必须幂等或具有明确的失败回滚策略。
- 删除世界记录不得自动删除世界文件、Git 仓库或完整备份。
- 清理操作需区分“从管理器移除引用”和“永久删除文件”。
- 导出诊断包时默认排除原始存档内容、个人绝对路径和任何不必要的用户数据。

### 15.1 高风险操作交互

- 确认对话框必须明确目标路径、影响文件范围、是否覆盖、是否存在可用保护备份。
- 危险按钮不能只依赖颜色区分；必须有明确动作文本。
- 默认选择最安全的非破坏性操作；用户取消后不得产生部分覆盖。
- 操作完成页提供结果、校验状态、日志位置和后续建议。

## 16. 技术架构与模块边界

### 16.1 推荐技术栈

| 层 | 推荐方案 | 理由/约束 |
|---|---|---|
| 桌面壳 | Tauri 2 | 轻量桌面应用，Rust 后端与跨平台分发。 |
| UI | React + TypeScript | 组件化界面、类型约束和成熟测试生态。 |
| 样式 | Tailwind CSS + 可访问组件体系 | 一致的桌面交互与主题能力。 |
| 核心服务 | Rust crates | 文件系统、进程管理、归档、哈希和跨平台系统接口。 |
| 元数据 | SQLite + SQLx | 本地优先、事务、schema migration。 |
| Git | 优先调用系统 Git CLI；启动时检测版本与可用性 | 利用成熟 Git 实现；所有参数必须安全传递，不拼接 shell 字符串。 |
| 文件监控 | Rust notify 或平台适配器 | 统一文件事件，仍需独立稳定性判定。 |
| 归档 | TAR + Zstandard + SHA-256 | 可验证的独立完整备份。 |
| 测试 | Rust 单元/集成测试、前端组件测试、Playwright/E2E | 覆盖核心流程和跨平台行为。 |
| CI/CD | GitHub Actions 或同等 CI | 构建、测试、签名/打包与发布产物校验。 |

### 16.4 关键接口边界

- `WorldScanner`：输入存档根目录与版本适配器，输出世界/角色候选、关联置信度和未知文件集合。
- `SnapshotCoordinator`：协调游戏进程状态、静默窗口、Git 提交与备份任务。
- `DiffAnalyzer`：生成只读结构化报告；不得修改源存档。
- `CommitMessageGenerator`：输入结构化报告，输出可编辑文案。
- `BackupWriter` / `Verifier` / `Restorer`：职责分离；恢复只接受已验证清单。
- `GameAdapter`：按游戏分支/版本提供路径规则、配置识别与解析器能力。

## 17. 安全、隐私与威胁控制

| 风险 | 控制要求 |
|---|---|
| 备份/归档路径穿越 | 解包时规范化相对路径；拒绝绝对路径、`..` 穿越、重复路径与危险链接。 |
| 误删或覆盖存档 | 恢复前保护当前状态；高风险操作预览、二次确认和审计。 |
| 下载资产被篡改 | HTTPS、校验摘要；可用时验证上游签名；校验来源与资产元数据。 |
| 命令注入 | 避免 shell 拼接；使用参数数组调用 Git/游戏进程；验证路径和参数。 |
| 敏感信息泄露 | 日志默认不写存档内容；诊断包最小化；远程 AI 摘要需明确授权。 |
| 资源压缩包恶意内容 | 限制解包路径、文件数、展开后大小、嵌套深度和符号链接行为。 |
| 数据库损坏 | 事务、迁移备份、启动完整性检查；数据库失败不触碰原始存档。 |
| 恶意/损坏存档输入 | 解析器使用边界检查、大小限制和错误隔离；未知格式作为不透明文件保留。 |

### 17.1 权限与秘密

- 应用不要求管理员/root 权限完成常规存档管理。
- 下载凭证、令牌等秘密不得写入普通日志或环境档案。
- 如未来加入云服务，凭证应使用平台安全存储，并提供撤销能力。
- 默认不自动上传存档、遥测或诊断信息。

## 18. 非功能需求与质量属性

| 类别 | 需求 |
|---|---|
| 可靠性 | 备份、恢复、检查点任务具有明确状态；不得静默失败。 |
| 性能 | 常规 UI 操作不被大文件哈希/压缩阻塞；后台任务支持取消和进度报告。 |
| 可恢复性 | 任何覆盖式恢复前必须有保护策略；备份可独立校验与恢复。 |
| 可维护性 | 核心业务规则位于 Rust domain/service 层，不散落于 UI 组件。 |
| 可移植性 | 核心领域逻辑不依赖特定操作系统路径；平台差异通过适配器封装。 |
| 可访问性 | 键盘导航、可见焦点、语义标签、非颜色单一状态指示。 |
| 可诊断性 | 结构化日志、错误码、任务 ID、可导出的最小化诊断包。 |
| 隐私 | 本地优先；联网功能可关闭；远程分析需明确授权。 |
| 兼容性 | 游戏格式解析器版本化；未知格式降级而非破坏性处理。 |
| 可升级性 | 数据库、备份清单、环境档案均有 `schema_version` 和迁移策略。 |

### 18.1 性能基线（初始目标）

> 以下是待通过真实样本校准的工程目标，不应作为未经测量的性能承诺。

| 场景 | 初始目标 |
|---|---|
| 冷启动（不扫描大目录） | 常见开发机上 3 秒内可交互；后台扫描另行显示进度。 |
| 常规元数据查询 | P95 < 200 ms（本地 SQLite，小规模工作区）。 |
| 文件变化响应 | 静默窗口后 2 秒内进入稳定性评估；实际快照时间取决于数据量。 |
| 取消备份 | 在当前安全取消点停止；不得留下可被误认作有效备份的最终文件。 |
| 大目录扫描 | 后台执行、可取消、显示进度和错误汇总。 |

## 19. 可观测性、诊断与支持

- 所有后台任务拥有 `task_id`、操作类型、目标、开始/结束时间、状态和错误码。
- 日志按级别区分，默认不记录角色内容、地图内容或敏感绝对路径。
- 提供“复制诊断摘要”与“导出诊断包”；导出前展示内容清单。
- 错误信息应包含可执行建议，如检查权限、释放磁盘空间、关闭游戏或选择有效目录。
- 支持用户查看当前备份健康、上次验证时间、未验证备份数和监控状态。

## 20. 测试策略与验收标准

### 20.1 测试层次

- 单元测试：世界边界识别、路径规范化、哈希、摘要模板、状态机、保留策略。
- 集成测试：Git CLI、SQLite、归档写入/校验/恢复、进程监测、文件监控。
- 格式兼容测试：使用经过授权或自行生成的脱敏/合成存档样本覆盖已支持版本。
- 端到端测试：导入游戏、识别世界、创建检查点、生成摘要、备份、恢复和启动验证。
- 故障注入：磁盘满、权限撤销、进程强杀、文件并发变化、损坏归档、数据库迁移失败。
- 跨平台测试：macOS Apple Silicon、Windows x64、Linux x64；其他架构按发布支持矩阵执行。

### 20.2 发布阻断验收

| ID | 验收条件 |
|---|---|
| AC-001 | 可导入首要验证环境中的游戏安装，并显示识别结果与未知项。 |
| AC-002 | 可识别至少一个测试世界；角色绑定不确定时不会伪造确定关系。 |
| AC-003 | 可创建世界级 Git 检查点，并生成文件级摘要。 |
| AC-004 | 对受支持样本可生成角色/世界结构化差异，摘要能追溯到解析器与字段。 |
| AC-005 | 游戏运行期间不会把自动检查点标记为权威稳定快照。 |
| AC-006 | 可创建独立完整备份，生成清单并完成 SHA-256 校验。 |
| AC-007 | 可在空目录恢复备份，并验证恢复文件与清单一致。 |
| AC-008 | 恢复前会保护当前数据；保护失败时默认中止覆盖。 |
| AC-009 | 损坏备份、路径穿越和中途退出测试不会导致源存档被覆盖。 |
| AC-010 | Git 仓库不可用或摘要分析失败时，独立完整备份仍可工作。 |
| AC-011 | 离线环境可使用本地游戏库、Git、备份和恢复功能。 |
| AC-012 | 用户可导出环境档案，并在导入时看到缺失资源与版本差异。 |
| AC-013 | 所有高风险操作均有审计记录和可读失败原因。 |

### 20.3 验收数据集

应建立不含真实玩家隐私的合成/脱敏测试集：单世界单角色、多角色世界、同名角色的不同世界、未知文件、空世界、文件持续变化、损坏 JSON/二进制、符号链接、极长路径和大小写差异。真实存档只在用户明确授权且遵循最小化原则时用于本地测试。

## 21. 发布、升级与兼容性策略

- 发布矩阵明确列出操作系统、CPU 架构、最低系统版本、安装包类型和签名状态。
- macOS 发行包优先支持 Apple Silicon；是否支持 Intel macOS 需根据构建与测试能力另行声明。
- Windows 与 Linux 作为目标平台，正式发布前必须通过核心备份/恢复验收。
- 每个版本发布说明列出新增能力、已知问题、兼容性变化、数据库迁移和备份格式变更。
- 数据库迁移前备份元数据数据库；应用升级不得修改或清理原始游戏存档。
- 备份格式必须向后兼容，或提供显式迁移工具和旧版恢复说明。
- 发布产物应提供校验摘要；支持的平台尽可能使用代码签名和可信发布流水线。

## 22. 里程碑、优先级与交付物

| 阶段 | 范围 | 完成条件 |
|---|---|---|
| P0：需求与风险验证 | 确认首要游戏版本目录布局、世界/角色识别策略、样本格式和备份恢复威胁模型 | ADR、样本集、兼容性记录、验收计划完成。 |
| P1：应用骨架与游戏库 | Tauri、SQLite、导入安装、启动、进程监控、操作日志 | 首要环境可导入并启动；路径和状态可靠。 |
| P2：世界发现与 Git | 世界/角色模型、稳定性状态机、Git 检查点、文件级摘要 | 世界级检查点可用；摘要失败不阻断提交。 |
| P3：独立备份与恢复 | 归档、清单、校验、恢复、故障注入 | 完整备份与空目录恢复通过发布阻断验收。 |
| P4：资源与环境档案 | mods、soundpacks、tilesets、fonts、档案导入导出 | 资源引用、兼容性提示与迁移预览可用。 |
| P5：结构化摘要与多平台 | 角色/世界解析器、Windows/Linux 构建与测试 | 解析器可追溯；三平台核心测试通过。 |
| P6：增强功能 | 统计、AI 润色、更多游戏分支、可选远端目录 | 均为可选功能，不削弱离线核心能力。 |

### 22.1 首发范围冻结建议

首发应优先交付：游戏导入/启动、世界发现、世界级 Git 检查点、文件级 commit 摘要、进程退出后的稳定性判定、独立完整备份、校验、恢复前保护、恢复验证、操作日志和基础环境档案。结构化存档解析按已验证格式逐步加入，不应以猜测式解析阻断安全能力。

## 23. 风险、假设与待决事项

| 风险/事项 | 影响 | 处理策略 |
|---|---|---|
| 不同 CDDA 版本存档布局不同 | 世界/角色边界可能误识别 | 版本化 GameAdapter；未知格式降级；建立真实测试样本。 |
| 运行时存档不一致 | 恢复后世界状态异常 | 进程检测 + 静默窗口 + 文件稳定判定；标记尽力快照。 |
| Git 仓库增长 | 磁盘空间膨胀 | 可视化仓库大小、保留策略、维护建议；不自动危险清理。 |
| 大型地图文件导致提交慢 | 用户体验下降 | 后台任务、进度、可取消安全点、性能测量。 |
| 跨平台路径差异 | 迁移失败或文件名损坏 | 迁移预检、冲突报告、源保护。 |
| AI 摘要幻觉/隐私 | 误导用户或泄露数据 | 默认模板、结构化输入、明确授权、失败回退。 |
| 上游发行/下载接口变化 | 自动安装失效 | 下载适配器与版本化源配置；保留手动导入路径。 |
| 许可证/商标问题 | 发布合规风险 | 独立实现；核实依赖和资源许可证；清晰声明非官方项目。 |

### 23.1 待决事项

- 首发是否采用每个世界独立 Git 仓库（当前建议：是）。
- 默认自动检查点的触发条件与静默窗口长度，需要真实存档测试校准。
- 首发是否内置 Git，还是要求用户安装系统 Git（当前建议：先检测系统 Git，必要时评估随应用分发）。
- 远端发行源与资源目录的最终名单及许可证审核。
- 开源许可证建议 MIT 或 Apache-2.0，需在确认依赖、品牌和分发策略后定稿。
- 是否支持 macOS Intel、Linux ARM64 等额外架构，应以实际 CI 和发布验证决定。
