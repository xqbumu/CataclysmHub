# 活动资源占用与保守调度

状态：已实现占用投影与统一冲突入口；按目录并发调度尚未实现。schema 8 不变。

## 持久化边界

会话和任务表是占用的唯一事实来源。`resource_claims.sql` 在同一 SQLite 快照中将活动所有者投影为 `ResourceClaim`，没有独立租约表、到期时间或可被前端修改的验证状态。启动/任务意图与审计提交后，其占用立即可查询；终态与结果审计事务提交后，占用自动消失。因此不会出现任务已记录但遗漏另写锁记录，或结果已落库但漏删锁记录的第二套生命周期。

现有进程内 mutation 门串行化启动/任务准入，元数据目录文件锁阻止第二个 Hub 写入者。所有启动预览、确认执行和文件任务继续通过统一的 `check_resource_claims` 检查。此模型不是跨机器分布式租约，也不是文件系统/操作系统强制锁。

| --- | --- | --- | --- |

每个活动所有者始终有全局独占声明；目录声明是已知保护范围的说明，不能视作完整游戏写入证据。普通任意参数启动尤其可能写入声明之外。未重新探测物理目录身份，不基于字符串目录差异授权并发；已存在的实例启动目录身份检查仍照常执行。元数据自身写入由数据库事务及单写者文件锁管理，不作为玩家目录声明列出。

`Dashboard.resource_claims` 与会话/任务历史在同一数据库快照读取，不受历史分页数量限制。游戏库列出占用者、已知目录、读取/可能写入及未知状态；即使未知会话已不在最近 50 条历史里，也可通过占用列表进入已有的人工关闭确认。面板最多展示 50 个所有者，显示完整总数，后端判定不截断。

## 释放与恢复

- 取消请求仅进入 cancelling，仍占用资源，直到 worker 结束并记录终态。
- 已结束 worker 的终态写入失败时，按所有者种类与 ID 过滤既有 runtime recovery 覆盖，避免虚假的活动任务。保留失败记录供重试写入，绝不重放文件操作。
- 进程结果无法持久记录时继续保留会话占用。等待子进程失败也保持 interrupted_unknown，不能因时间、PID 消失或应用重启推断安全。
- 重启将旧任务对账为 recovery_required，不自动重放；旧 starting/running 游戏对账为 interrupted_unknown，保留全局保护。人工确认与审计原子提交为 resolved_unknown 后释放；不因此标记存档稳定或绑定验证通过。
