# 新目录恢复核心与独立工具

状态：WP-10 非覆盖恢复核心、独立 CLI 与桌面任务流程已实现。原目录替换与回滚未开放。源为应用生成的 v1 save_root TAR+Zstandard，目标为用户明确指定的全新容器目录。恢复不打开 SQLite 或 Git，不把目标自动绑定成当前游戏存档。

## 使用与结果

```sh
cargo run -p hub-core --bin restore-backup -- /path/to/backup-id /path/to/new-recovery --confirm-new-directory
```

要求目标的父目录已存在，目标本身不存在。拒绝已有空目录、非空目录、目标链接，以及目标与源备份目录的包含关系。现有目录的子级可以作为新的容器，但绝不把其内容混入已有存档。容器包括：

- `data/`：恢复的原始文件字节和空目录。
- `RESTORE_INCOMPLETE.json`：工作开始后同步写入的未完成标记；失败时保留，若最终同步失败则尽力恢复标记。
- `restore-verification.json`：全部回读验证后写入的结果；成功时移除未完成标记。仅当命令成功退出、无未完成标记且有验证结果时，视为本次恢复完成。

结果记录备份 UUID、归档/清单摘要、文件/条目/字节数、原始一致性等级及验证时间。verified 是文件完整性结论，原 best_effort 不会因恢复自动升级，不表示游戏语义、来源可信或版本兼容。报告只描述生成时的状态，后续人工编辑不会自动更新报告。

## 实现与安全边界

1. 规范化源目录与目标父目录，用能力目录句柄执行后续路径操作，预先拒绝覆盖与重叠。
2. 使用已有读取器完整验证归档，校验外部回执（若存在）、内部清单、精确条目集合、类型、大小、文件哈希及 Zstandard 结束。回执不存在仍能依靠内部清单恢复，不等于认证来源。
3. 检查目标可用空间（清单总量 + 16 MiB 预留），独占创建容器、同步未完成标记与父目录。空间检查不能预防后续耗尽。
4. 共用同一个归档解析器进行二次验证和解包，绑定第一次归档摘要，拒绝中途换包。只创建清单中的目录和普通文件；文件 create_new，路径逐层 nofollow。无通用 tar.unpack，没有权限/链接/特殊设备条目的隐式恢复。
5. 边写入边检查每个载荷哈希并同步文件；归档结束和再次整体摘要检查后，从目标重新枚举并回读所有文件，对照精确路径、类型、大小与 SHA-256。同步子目录到根目录。
6. 同步结果报告，再移除未完成标记并同步容器与父目录。失败不删除部分数据、不自动重新执行；选择另一个新目录重新开始。

目标文件系统不支持名称时直接失败；大小写/Unicode 别名导致 create_new 或目录创建冲突时中止，不静默合并、覆盖或改名。当前是写入期间探测，桌面接入前仍需完善平台名称碰撞预检。只恢复普通文件内容和空目录；不恢复 ACL、扩展属性、原始权限、硬链接、稀疏布局和时间戳。

临时容器在操作期间可见，不宣称目录重命名发布的原子性。最终标记和载荷不能与 SQLite 形成跨介质原子事务；本工具没有 SQLite 依赖。目录同步目前在 Unix 执行，Windows、网络盘、拔盘与真实掉电仍待平台验证。若标记写入/同步也失败，可能只留下空容器或不完整记录，不能仅按目录名称判断成功。操作不防御拥有同等文件系统权限的并发恶意进程；恢复时应关闭外部写入者。

## 验证与后续

回归覆盖未知二进制、无效 JSON、中文/长文件名、空目录、空归档、回执丢失、已有目标、链接目标、路径穿越、归档损坏、大小写碰撞和命令行确认。macOS 上使用先前原生应用创建的 3 文件 / 5 条目 / 55 B 归档执行独立恢复；额外 Python 枚举对比源与恢复目录的精确路径、类型与 SHA-256，全部一致。

桌面恢复已支持原生父目录选择、过期计划、用户确认、持久任务/取消/中断记录、操作审计与结果展示，详细机制见下文。覆盖恢复另需保护备份、替换 journal、故障注入和回滚证明；本切片不包含这些能力，不标记 WP-10 或恢复相关 AC-007～AC-009 全部完成。


## 桌面计划与任务（schema 4）

桌面只从已登记归档发起恢复：选择父目录后，后端生成 restored-{uuid} 新容器名，检查目标与当前存档/备份/资源/元数据根目录不重叠，并校验已登记的归档/清单摘要。预览是只读操作，不创建容器或任务。新的随机目标名不能由前端任意改成现有目录。

计划保存在内存，5 分钟过期、最多 32 份，摘要覆盖完整计划。保留源归档目录与目标父目录能力句柄，并通过 same-file 比较父目录身份；预览后同一路径被替换为另一目录也拒绝执行。计划重启失效；已持久任务可通过原请求标识与摘要查询重放结果，不能重复执行。

新增 prepare_restore / start_restore / cancel_restore IPC，仍使用现有 Result DTO 适配层；不表示生产 IPC 全量契约已经完成。prepare_restore 只接受本机选择器授权过的父目录。确认与摘要由后端强制验证，创建任务与开始审计在同一个 SQLite 事务中提交。restore_task 单独表保存目标完整路径、备份 ID、请求摘要、状态、阶段、修订号及错误；历史列表最近 20 项，通过 dashboard 轮询，不返回存档内容。预览包含私有路径，仅本地显示。

阶段为准备、归档重新验证、写入新目录、恢复文件回读验证和结束。阶段显示不冒充精确字节百分比；预检与阻塞 OS 调用暂不能强制中断。归档验证失败会撤销当前健康状态，访问失败记 unavailable；目标磁盘故障不改写源归档完整性结论。

共用全工作区后端互斥门，恢复期间禁止新扫描、备份、恢复和游戏启动。文件完成后先保留未完成标记；在取消/完成互斥门内决定是否写入成功报告及移除标记，再记录终态与审计。取消先到则不发布成功标记；完成先到则取消返回真实成功终态。阶段写入失败会请求停止并报告记录失败；终态写入失败使用运行时 recovery_required 叠加与仅重试状态记录的已有机制，不重新写文件。文件系统完成和数据库提交仍不是一个原子事务，可能留下已验证目录但任务需要检查。

schema 1/2/3 升级前创建校验过的 VACUUM 元数据副本，同一迁移事务追加 restore_task；失败不改变旧版本。重启将 running/cancelling 恢复任务标为 recovery_required/TASK_INTERRUPTED，并保留目标目录和审计。不自动重放、清理、重建成功结论或切换当前存档。

本机验收：原生应用从 schema 3 元数据迁移到 4；预览前后恢复目录与任务表均无新增，确认后产生 succeeded 任务及开始/终态审计，UI 显示“恢复字节已验证”及兼容性未知。独立 Python 检查原存档未变、恢复树 3 文件 / 5 条目 / 55 B 的路径/类型/摘要完全一致，迁移前 schema 3 快照 quick_check 通过。已加入摘要篡改、父目录替换、目标抢占、源归档变化、取消边界、互斥、终态持久化故障、请求重放、重启中断及迁移回滚测试。
