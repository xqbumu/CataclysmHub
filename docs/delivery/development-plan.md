# 开发路线图与可排期工作包

版本：0.1.0 · 日期：2026-10-27 · 状态：待评审 · 责任角色：产品、技术、QA 负责人。依据：PRD §22；阶段编号使用 M，区别于功能优先级 P。

## 排期假设与关键路径

在人员、预算、目标日期尚未提供时采用依赖驱动计划，不虚构承诺日期。下表相对规模 S/M/L 表示低/中/高复杂度，不是人日估算。M0 完成后由执行团队按真实能力估时，并单列跨平台、签名及样本获取的外部等待。

关键路径：版本/路径验证 → 工作区与任务基础 → 世界边界和冻结副本 → 独立备份 → 受保护恢复 → 故障注入 → 三平台验收与发行。Git 与摘要不能成为独立备份的必需依赖。

| 阶段 | 目标 | 退出条件 |
|---|---|---|
| M0 风险与契约验证 | 样本、技术栈、路径/进程能力、设计评审 | 关键 ADR 和格式评审；真实样本边界有证据；待决项有负责人 |
| M1 应用骨架 | 工作区、元数据、任务、安装与启动 | 首要平台导入启动与任务重启可观测 |
| M2 世界与历史 | 世界识别、稳定性、冻结副本、Git/模板 | 世界隔离、完整提交、降级测试通过 |
| M3 独立备份与恢复 | 清单、归档、校验、保护、重启恢复 | AC-006～010 及中断恢复通过 |
| M4 资源与档案 | 本地资源、档案、迁移预览 | AC-012、MOD/MIG 对应验收通过 |
| M5 结构化摘要与正式发行 | 已验证解析器、三平台、签名与性能 | 全部 AC 和正式发布门禁通过 |
| M6 可选增强 | 下载目录、统计、AI、更多分支 | 每项独立开关和隐私/离线回归通过 |

## 建议迭代切片

第一条可演示切片只完成“导入一个现有安装→启动→看到运行/退出状态及审计”。第二条完成“确认世界范围→冻结副本→独立备份→恢复到空目录”，可先于完整历史 UI 完成。第三条完成“当前世界保护→恢复→强杀重启→回滚”。此后再扩展 Git 历史、资源、结构化摘要和多平台，避免界面完成而恢复机制未验证。

每个迭代结尾演示正常、取消、故障三条路径；迭代评审关注证据和风险收敛，不以页面数量衡量进度。

## 子任务模板与估算

工作包细化为可独立评审的 issue：用户结果、需求 ID、输入/输出契约、依赖、正常/异常/取消/重启验收、测试数据、文档更新、Owner、估算区间。使用 [工作项模板](../templates/work-item.md)。本交付只建立本地计划，未在远端创建 issue。

M0 的估算校准至少包含 1/10 GiB 合成世界、文件数量变化、Git 重复提交增长、三平台构建时长及恢复故障调试。样本量、工具版本和硬件一起记录，避免将一台机器的耗时直接用于所有环境排期。


## 2026-10-28 用户确认顺序与版本/存档约束

按“保留只读预览 → 后端保护 → 安全隔离/删除 → 受保护覆盖恢复”推进。版本管理与存档影响已经在 GAME-002/004/005/007、§11/13 和 MIG-001/002/004 中，不作为可选下载或 AI 的附属功能。

只读预览先以 unknown/unverified 显示缺失环境，不能产生删除授权。后端保护阶段同步补最小安装身份/版本证据、存档绑定、环境引用和升级前保护引用；危险清理、受控升级/切换和覆盖恢复执行前必须具备对应保护与介质复检。完整资源档案仍按 WP-12/13，迁移按 WP-14，下载发现仍可后置。

具体能力、现有缺口、版本差异/兼容性区分和验收门见 [游戏版本与存档影响](../design/version-save-impact-scope.md)；本轮只读规则范围见 [保留预览](../design/retention-preview-implementation.md)。本排序不把“显示一个版本名”或“文件相同”视为已完成版本/存档兼容管理。

用户随后明确增加 USR-001“多版本并发游玩”。将独立游玩实例、实际存档/配置写入范围及按范围锁纳入上述第 2 阶段的版本关联基础；该基础应先于安全删除和受控版本切换开放。多安装并存不算并发验收，当前全局会话互斥尚未放开。验收见 [需求补充](../requirements/multi-version-concurrent-play.md)。

USR-001 的实现归入 WP-03/04/05 的范围锁、安装身份与存档关联基础；下一开发重点先完成这一基础，再扩展 WP-11 的危险清理执行。

2026-10-28：实例登记后已补受全局保护的源码参数试运行与实例会话关联；真实目录绑定、安装缓存和并发仍未验收。下一项优先明确构建来源与实际写入证据、处理 base/data 缓存共享，再实现按范围租约和实例备份，不先开放危险清理。见 [试运行设计](../design/instance-launch-trial.md)。


2026-10-28：已取得官方 macOS H/I-1 样本并形成独立 QA 启动器下的双世界保存/重载、退出隔离与范围对比证据，补 macOS 框架路径和确认后目录准备。下一阶段重点从源码参数试运行转为持久资源租约：安装 base/data、实例玩家数据及未知全局范围全部参与冲突与恢复，再做 Hub 真实双开和按实例备份验收。具体实施门见 [真实游戏验收](../quality/real-game-binding-acceptance.md)；不得直接移除旧全局锁宣称支持并发。

### 活动资源占用接入（2026-10-28）

已从持久会话/任务状态派生统一占用投影，启动和所有文件任务使用同一准入入口；游戏库解释占用及已知目录，支持历史列表之外的未知会话确认。取消中保护、重启对账与结束 worker 的记录失败覆盖沿用原子状态生命周期。没有另建租约表，仍全局互斥；不能将本切片当作目录冲突判定、适配器验证或 Hub 并发已完成。下一步仍需验证写入边界/共享安装缓存策略，之后实现按物理范围调度及实例备份，再执行 Hub 双开验收。详见 [实现边界](../design/resource-ownership.md)。

### 物理目录冲突预检接入（2026-10-28）

游戏库可只读检查指定实例的安装目录、实例根与全部活动占用，识别物理共享/嵌套/别名和无法核实范围，并在实例启动预检与确认执行时复用。当前全局未知占用及任务串行保护均保留，无冲突报告不授权并发。下一步仍是完整写入边界与共享安装缓存策略、执行期范围保护和实例备份；在这些条件具备后才撤销相应全局限制并进行 Hub 内真实双开验收。见 [预检实现](../design/instance-resource-conflicts.md)。

### 开源复用与锁诊断结论（2026-10-28）

不迁移技术栈，也不将引入沙箱工具直接视为并发通过。按 [候选评估](../research/open-source-isolation-options.md) 保留 cap-std/same-file；Catapult/Prism 用于布局和实例模型参考；Linux 对 bubblewrap 单独做策略及图形/子进程负例；macOS 先验证每实例完整安装副本，避免仍可能写入的文件使用硬链接共享，再结合玩家目录、HOME/临时目录及包内动态库边界验证。实例备份继续基于现有恢复契约扩展，restic 只作为未来独立后端候选。

工作区锁的正常释放缺口已用显式解锁 guard 修复并完成确定性负例和 120 轮压力复测，不采用换库、延时或取消单写者约束的办法。后续优先完成安装副本范围/来源记录与受控实例备份，再推进执行期按范围保护和 Hub 内真实双开；未知写入仍保留全局声明。
